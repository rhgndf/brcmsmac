# BCM43227 support in brcmsmac

Target: PCI `14e4:4358` (subsystem `105b:e040`), BCM43227 rev 0 package 8,
D11 core rev 30, N-PHY rev 16 (LCNXN, normalised +16), analog rev 9,
radio 2057 rev 9 version 1, 2.4 GHz only, two chains, SPROM rev 8,
`extpa_gain=2` (internal PA on 2.4 GHz).

Constraints:

- brcmsmac is ISC. b43 is GPL-2.0-or-later. b43 code and findings may be
  used; each commit that does names what it took from b43 and where.
- Values for this chip come from the reference MMIO capture of wl
  6.30.223.271 (firmware 832.127) on this card
  (`../b43/.work/captures/wl-init-ht20-ch6-02/` and the later wl captures
  next to it), from existing brcmsmac, or from b43.
- No proprietary source, disassembly or decompilation. wl is observed only
  as a black box: MMIO, DMA and over-the-air captures. Firmware is taken
  unmodified, by symbol name, from `wlc_hybrid.o_shipped` of the
  broadcom-wl 6.30.223.271 package (`../broadcom-wl-dkms`, installed at
  `/usr/lib/broadcom-wl-dkms/wlc_hybrid.o_shipped`).
- The port series (up to `800781c`) was verified without loading the
  module: build (W=1), checkpatch, and scripted re-derivation of every
  data table. Every later commit was tested on the card in the lab
  described below.
- Each commit builds, keeps existing devices unchanged, and is reviewable
  alone. The device is bound only by `800781c`.
- Pre-existing brcmsmac bugs are not fixed here; they are listed in
  [EXISTING_BUGS.md](../EXISTING_BUGS.md). A fix that a new feature
  cannot work without stays in that feature's commit and says so.

Why brcmsmac rather than b43: [bcm43227-feasibility.md](bcm43227-feasibility.md).

## Firmware

wl 6.30.223.271 ships, in brcmsmac's native layout (LE32 ucode words;
`struct d11init` LE16 addr/size + LE32 value, `0xffff` terminated):

| Symbol | Size | Use |
| --- | --- | --- |
| `d11ucode30_mimo` / `d11ucode30_mimosz` | 40640 B | core 30 N-PHY ucode |
| `d11n16initvals30` | 3784 B | core init values |
| `d11n16bsinitvals30` | 288 B | band init values |
| `d11ucode_ge24_bommajor/minor` | 832 / 127 | version |

The capture used this same firmware, so its SHM/descriptor ABI is the
reference for the MAC side.

## Commit series

1. [x] 32-bit DMA mask. brcmsmac drops bits 32-63 of DMA addresses but
   never set a mask; after b43 (64-bit mask) had been bound, the RX ring
   landed above 4 GiB and the engine stopped with a descriptor protocol
   error every second. `2cbad90`
2. [x] Load core rev 30 firmware: four new section tags in
   `brcm/bcm43xx-0.fw`, looked up only on core rev 30 after the existing
   ones, so an image without them still loads elsewhere; ucode/initvals/
   bsinitvals selection in `main.c`. `204faef`; ucode words and both
   initval sets verified write-for-write against the wl trace (lines
   874-11036, 11057, 11688).
3. [x] Core rev 30 TX FIFO sizes 9/98/22/14/14/5, identical to the
   sequence `brcms_b_corerev_fifofixup()` emits (trace 11529-11564).
   `6e63567`
4. [x] Constify 2057 init tables (prep). `bea1b42`
5. [x] Radio 2057 rev 9: init table, RCAL, RCCAL tail, channel setup
   overrides. `7a427c7`. Rev8 channel table reuse verified correct
   apart from TXMIX2G/PAD2G, which the overrides set.
6. [x] Out-of-tree only: tool appending the core rev 30 sections to
   linux-firmware's `bcm43xx-0.fw` (b43-fwcutter does not know the

10. [x] Enable N-PHY rev 16 in `NCONF`. `bbd1ba7`. All 31 distinct
    `NREV_*()` tests evaluate identically for revs 0-8 under the old and
    new mask; for rev 16 each equals the plain comparison.
11. [x] MAC changes required by firmware 832.127: energy-detect carrier
    sense (`IFS_CTL1_EDCRS`) on core 30, set both in IFS_CTL1 and in SHM

    (brcmsmac's 2048 is longer), M_AGING_THRSH 0x320, M_RADIO_PWR 0x480
    (brcmsmac never writes them for any chip).
12. [x] Bind BCM43227: BCMA core rev 30, PCI ID `0x4358`
    (`BCM43227_D11N2G_ID`), `D11CONF` bit 30, `MAXCOREREV` 31. `800781c`

## Lab testing

The BCM43227 is a station in the root network namespace (192.0.2.2). The
peer is an RTL8812AU (rtw88) in network namespace `b43-peer` running
hostapd as an access point (192.0.2.1): `b43-lab-43227`, channel 6, HT20,
WPA2-PSK CCMP, `[SHORT-GI-20]`, beacon interval 100 TU, DTIM period 2.
For 40 MHz, `.work/hostapd-ht40.conf` runs HT40- on channel 6 and
`.work/tmp/hostapd-ht40p-ch1.conf` HT40+ on channel 1. The station's
wpa_supplicant configuration pins 2437 MHz, so channel 1 needs
`WPA_CONF=.work/tmp/wpa-anyfreq.conf`. A home TP-Link access point
(HT20) with a wired iperf3 server served as a second peer.
Throughput is iperf3 TCP over 8 s unless noted, TX meaning from the
BCM43227 to the access point. Numbers vary by ±10 Mbit/s from run to run,
so each comparison alternates builds over several rounds.

| Commit | Result |
| --- | --- |
| `c7fc751` delimiters | The access point advertises 16 µs MPDU spacing. During bidirectional TCP, in-window members acknowledged by Block Ack rose from 91% to 99.5%; members sent outside the Block Ack window after retransmissions fell from 8601 to 14 in 5 s. |
| `4a21d93` short GI | minstrel_ht settles on HT20 SGI MCS15 (65382 of 71001 attempts succeeded). TX rose from 45.4/56.2/54.7 to 60.2/51.5/64.7 Mbit/s over three rounds; RX and bidirectional unchanged. |
| `704d6e9` STBC | Against `[RX-STBC1]`, single-stream fallbacks go out as STBC on both antennas while MCS15 stays SDM. MCS7 pinned: TX mean 40.3 → 43.1 Mbit/s over four rounds; no reliability gain at short range. No regression under rate control. |
| `7e0c58f` CCMP | Pairwise key in slot 4, group key in slot 2; software CCMP no longer runs (0 against ~200000 `ccmp_special_blocks()` calls per round). TX 65.6-75.2, RX 56.7-63.3 Mbit/s, unchanged. 398/400 pings over four group and two pairwise rekeys; a mac80211 restart lost 1/150 pings and restored all keys. |
| `100090e` A-MSDU RX | With A-MSDUs outside A-MPDUs (lab rtw88 change), UDP at MCS7 lost nothing and TCP reached 42.4-44.0 Mbit/s, against no data before. At 54 Mbit/s with 5-7 kB A-MSDUs, 0.1-1.9% of UDP was lost, with FCS errors counted by the microcode; not fixed. |
| `788dec0` power save | Idle in dynamic power save the microcode slept in 98/100 samples and received 48 of 49 DTIM beacons in 10 s; ping 3.1-8.7 ms to the AP, 9.3-211 ms from it. Static: 48/50 asleep, 49/49 beacons, 43.7 kbit/s TCP download. The first ping from the AP after turning power save off: 0.83-0.91 ms (8/8). 48 of 48 TCP runs alternating power save off/on completed at unchanged throughput. One earlier soak of the same build stopped delivering data to the AP after its first round (the AP acknowledged the frames but passed none up); it did not recur. |
| `c270b53` LED | Loaded before the PCI device is bound to bcma, brcmsmac logs "led GPIO chip not registered", binds, scans and unloads cleanly instead of oopsing in `gpiochip_request_own_desc()`. |
| `c1590ad` PHY calibration | Under NetworkManager, the RX IQ coefficients (PHY 0x9a-0x9d) stayed 0 after the load and are now calibrated. Ping loss at a fixed MCS7 fell from 12% to 0-2%; a TCP download that had not completed in three tries ran at 35-37 Mbit/s (wl: 47). |
| `a45a108` retries to rate control | At 40 MHz, rate control now leaves MCS 15 short GI when its small aggregates fail. 100-byte UDP up 0.4-0.5 → 4.4-4.8 Mbit/s, TCP down 16.4-16.9 → 90.5-91.0 Mbit/s; BARs per 4 s at a fixed MCS 15 2117-2146 → 504-574. On the home AP (HT20), TCP down 30.8-38.8 → 42.7-63.7 Mbit/s over five rounds (wl: 57.6-70.2); TCP up unchanged at 18.4-25.1 (wl: 22.2-23.1). |
| `c7fc751` retried last MPDU | Two captures of 4096 TX headers at 20 MHz held 11 middle members without delimiters where 26 were needed, all retries; none after. The RTL8812AU acknowledged the following members anyway, so no throughput change. |
| `40373ea` 40 MHz PHY | The registers match wl at 40 MHz and return to the 20 MHz values when the AP switches back. No measurable effect at short range: TCP down 101-145 vs 114-133 Mbit/s without, up 71-94 vs 90-105; crsglitch, badplcp and badfcs counts the same. |
| `0cd5ae0` 40 MHz | HT40- channel 6, three rounds against three at HT20: TCP up 67-102.5 vs 60-68, down 92.6-111.6 vs 51.7-66.9, 100-byte UDP 5.7-6.1 vs 5.3-6.0 Mbit/s. HT40+ channel 1: up 94.7, down 107.1. Scans while associated work; after the AP restarts at another width the station reassociates within 4 s. Unaggregated CCK frames at 40 MHz are acknowledged. |

AP mode needs no change for this chip. With the BCM43227 running hostapd
(same settings) and the RTL8812AU as its client, WPA2 association, HT20
MCS15 short GI both ways, 71.8 Mbit/s to the client and 45.1 Mbit/s from
it. With the client in power save, unicast frames wait for the TIM and
arrive (28-210 ms pings), but broadcast frames are lost: brcmsmac sends
them before the DTIM beacon (EXISTING_BUGS.md).

Known lab behaviour that no commit addresses:

- Bidirectional TX starvation. With TCP in both directions at once, the
  BCM43227 transmits only ~1.5-3 Mbit/s against 20-80 Mbit/s received.
  Hypothesis, not verified: BE A-MPDUs are capped near 250 per second,
  and fq byte fairness lets the TCP ACKs of the download crowd out the
  upload's data.

Findings at 40 MHz:

- The hardware sends at most 63 null delimiters. With 64 or more in the
  TX header, every attempt ends in a TX PHY error. 100-byte UDP at
  MCS 13-15 short GI needs more for 16 µs spacing, so `0cd5ae0` caps the
  count. wl writes larger counts (87 and 105 at MCS 15), mostly uses
  MCS 13 with 60, and sends 100-byte UDP at 2.6 Mbit/s.
- Not adopted: after each 40 MHz channel set, wl also sets
  `IFS_CTL1_EDCRS_20L` and `IFS_CTL1_EDCRS_40` (0x003f in IFS_CTL1 and
  SHM `M_IFS_CTL1`, against 0x000f at 20 MHz). Writing them at run time
  had no measurable effect.
- Not adopted: HF4 bit 0x0020, which wl sets. With it, brcmsmac's
  traffic breaks.
- Left as is after a 40 MHz association: PHY 0x69, 0x222, 0x234, 0x323,
  0x324 and IHR 0x656/0x658 differ from wl, as do calibration results
  (PHY 0x9a-0x9d, 0x29c, radio 0x172). Writing wl's values into IHR
  0x656/0x658 and PHY 0x324/0x29c at run time did not change the
  TX PHY error rate.

## Open questions

Answered by the wl trace: the core 30 FIFO partition (9/98/22/14/14/5,
trace 11530-11564); SHM writes (same offsets and values, item 11); the
N16 -> radio rev 8 channel table reuse (correct apart from TXMIX2G/PAD2G,
item 5).

Answered in the lab: A-MPDUs are received and Block Ack sessions work in
both directions (TCP under rate control: RX 54-78 Mbit/s, TX 60-75
Mbit/s). Outside an A-MPDU the microcode delivers an A-MSDU as one DMA
frame per subframe (`100090e`). The joined frame takes RxTSFTime from
the last piece, and that is the start of the A-MSDU, like a whole
frame's. The first piece's RxTSFTime is stale: in 1232 of 3336 A-MSDUs
at MCS7 it equalled the previous frame's. Taking each frame's stamp plus
its airtime, the next frame's stamp came at least 90 us later (SIFS, ACK
and AIFS) between whole frames and with last-piece stamps, apart from 3
jumps of about 20 ms in each. With first-piece stamps, 726 of 3605 gaps
around an A-MSDU were shorter than 80 us, down to -340 us. b43's G13
assumed the reverse.

Still open:

- Delayed A-MPDU secondary TX status (brcmsmac gives up after ~10 us; the
  wl trace reads it immediately after the primary word).
- 832.127 A-MPDU TX descriptors (PreloadSize/MaxNMpdus/MaxABytes) were
  captured at 40 MHz (`.work/captures/wl-txdesc-ht40-ch6-01`) and used
  for the bandwidth fields and the delimiter count; the other fields
  were not compared against brcmsmac in detail.
- SPROM rev 8 per-rate power: read (`wlc_phy_txpwr_srom_read_ppr_nphy()`
  returns early only for rev >= 9), but its effect on output power is
  unmeasured.
- HF4/HF5 bits wl sets (item 11): HF4 0x0020 breaks brcmsmac's traffic;
  the others' effect is unknown.

## Out of scope for this series

- 5 GHz (the chip is 2.4 GHz only). 40 MHz on 2.4 GHz for other chips:
  `0cd5ae0` enables it only on core rev 30.
- Calibration refinements beyond what wl's init sequence shows.
